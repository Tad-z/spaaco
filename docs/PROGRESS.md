Notable: the rule needs `eslint-import-resolver-typescript`, because NodeNext imports are written `.js` while the file on disk is `.ts` — without it the zones match nothing and pass vacuously. sharp pinned to ≥ 0.35.4 (0.33 carries high-severity libvips advisories); `npm audit` is clean.
- **0.2 OpenAPI spec for the public API** — `openapi/openapi.yaml` (3.1) covering all 17 public operations, with 77 reusable component schemas, shared parameters and error responses; `npm run types:gen` emits `src/types/api.generated.ts` and `src/types/api.ts` aliases every schema. `npm run types:check` fails the build when the generated types drift from the spec. Notable: response examples are `$ref`s into `fixtures/responses/`, which Prism resolves but Redocly's `no-invalid-media-type-examples` cannot (it validates the literal `{$ref}` node), so that one rule is off and fixture/schema validation is done with ajv in the contract tests instead. Response fixtures landed in this commit because the spec cannot lint without them.
- **0.3 Fixtures from SEED_CONTENT.md** — 23 response fixtures in `fixtures/responses/` and 9 raw collection documents in `fixtures/seed/` (settings, practice areas, people, offices, recognitions, faqs, insights, jobs, pages), all transcribed from `docs/SEED_CONTENT.md` with `[PENDING FROM FIRM]` wherever the designs show nothing. The documented design conflicts (partner titles, the 15+ Areas stat, the identical NYSC job, the footer office order) are seeded as designed, per DECISIONS.
- **0.4 Mock server + frontend handoff** — `npm run mock` serves the spec on :4010; `curl localhost:4010/api/v1/pages/home` returns the home fixture byte-for-byte. Required moving the `/api/v1` prefix from `servers` into the spec's path keys, because Prism ignores a server base path and has no flag for it (ADR-019). `docs/FRONTEND_HANDOFF.md` documents the mock, the conventions, every endpoint, all 17 known placeholders and the not-yet-designed screens. Two mock limitations are called out there: `/pages/{key}` always serves the `home` example unless the request sends `Prefer: example=<key>` (Prism cannot select an example by path parameter), and query filters are validated but don't change the payload.

## Phase 1: Foundation

- **1.1 Config + logger + errors** — `config/env.ts` is the only reader of `process.env` (ESLint-enforced); it exports `parseEnv(source)` alongside the frozen `config`, so tests exercise both paths without mutating the real environment. Failures report _every_ bad variable at once, and two checks go beyond plain schema validation: selecting a driver without its credentials fails at boot rather than on the first request that needs it, and production refuses the `.env.example` placeholder secrets by value. `core/errors.ts` has one `AppError` subclass per spec error code, and its `toResponse()` bodies are validated against the spec's own `ErrorResponse` schema with ajv, so an error body that drifts from the contract fails a test. `core/logger.ts` redacts `req.body` wholesale rather than listing personal fields, so a new form field cannot leak on the day it is added. 72 new tests. Notable: `tests/support/setup-env.ts` runs via vitest `setupFiles` because config parses at import time.
- **1.2 App factory + middleware + health** — `createApp()` never listens, so Supertest drives the real middleware chain; `server.ts` adds graceful shutdown (stop accepting, drain, close the DB, hard-exit after 10s). Middlewares: request-id (validates and echoes a caller-supplied id, and defaults `preview` to false so a route that forgets preview auth hides drafts rather than leaking them), validate, not-found and the error handler — the single place an error becomes a response, where a non-operational error always yields the fixed 500 body. `/health` runs through route → controller → serializer → service as the reference example. Notable: writing it caught a real layer violation, because the serializer had imported its input type from the service; the type moved to `interfaces/health.interface.ts` and the ESLint zone flagged it, not review. `core/db.ts` was written here rather than in 1.3 because `server.ts` cannot exist without it. The typed `req.validated` readers carry the Zod schema as a type argument, which gives call sites the schema's real inferred type with no `as` cast and no second parse. One planned test was dropped as unreachable: Node refuses to transmit a header containing a control character, so that case is covered as a unit test of the middleware instead.
- **1.3 Database + test harness** — `setupTestDb()` runs a per-file mongodb-memory-server and empties collections after each test (deleteMany, not drop, so indexes survive); `expectToMatchContract(res, method, path)` validates a live response against the spec. The helper treats an unknown path, an unknown method and an undeclared status as hard failures, because a contract assertion that shrugs at a typo makes every test using it _read_ as covered while asserting nothing. Notable: its own test suite caught exactly that bug — every error response in the spec is a `$ref` into `components/responses`, so the first implementation found no `content`, assumed "no body" and passed silently on all error statuses. `tests/support/spec.ts` gained `pointerGet`/`resolveRef` to follow the indirection.

### Testing strategy change (ADR-029)

- **Test scope and speed** — at the project lead's request, coverage is now proved once in the cheapest place: per-endpoint tests are happy path + 400 + 404, draft exclusion is once per resource, role enforcement lives only in a future `tests/integration/admin/roles.test.ts`, and the CRUD factory is tested once with a one-line smoke test per collection. During a task only touched tests run; full `npm run check` is per phase; the api-reviewer runs at the end of Phases 3, 5, 6 and 7. Mechanically: one mongod for the whole run via `globalSetup` (per-worker databases, `afterEach` clears rather than drops so indexes survive), and the layer-boundary probes fold into a single ESLint run. Suite wall clock 7.3s → 6.3s today, and each new DB-backed file now costs ~0.1s instead of ~1s. Consolidated one true duplicate (the health happy path was asserted in both `app.test.ts` and `health.test.ts`); no role or draft duplicates existed yet, since no admin routes or content resources are built.

## Phase 2: Models and seed

- **2.1 Shared interfaces, plugins and sub-schemas** — `constants/enums.ts` types every enum against the spec (`satisfies readonly PersonRole[]` plus `Record<T, string>` for labels), so an invented value or a missing label fails typecheck; a unit test additionally compares each list against `openapi.yaml`, catching the reverse case the type system cannot — a value added to the spec and never added here. `helpers/slug.helper.ts` is pure; collision handling lives in `models/plugins/content.plugin.ts`, which is the only layer that can see the collection. Slugify drops apostrophes rather than splitting words (`nigerias-economy`, not `nigeria-s-economy`) and truncates at a word boundary with room reserved for a `-2` suffix, so a long title cannot produce a slug that breaks the contract's 140-char maximum. The plugin's pre-save check is backed by a real unique index, and a test inserts straight through the driver to prove the index — not just the lookup — is what guarantees uniqueness. 66 new tests; the content plugin is tested once here rather than per collection, per ADR-029.
- **2.2 Content interfaces + models** — eight interfaces and models (media, practiceAreas, people, insights, offices, recognitions, faqs, jobs) with every index from DATA_MODEL.md, plus `scripts/sync-indexes.ts` (`npm run db:sync-indexes`), which uses `syncIndexes` so a renamed or removed index is dropped rather than lingering. `constants/media-refs.ts` registers every media-bearing field; `tests/integration/models.test.ts` walks all registered schemas and fails if one is missing, and I verified that guard bites by removing `Insight.coverImage` and watching it fail. Notable decisions: `displayName`/`roleLabel` are not stored or even virtual — serializers derive them, per the models rule, so a label change needs no migration; person slugs come from a `fullNameForSlug` virtual so they read as a full name; recognition slugs combine organisation, title and year because four tiles share an organisation and title; office coordinates are validated as GeoJSON `[lng, lat]` with a test that a reversed pair is rejected; and `storageKey` is stripped in the media `toJSON` as well as in the serializer, so an internal path cannot reach a client by any route. `src/models/index.ts` is the one permitted barrel, because index sync and the media guard both need to enumerate models and `ref: 'Media'` only resolves once the target is registered. 29 new tests.
- **2.3 Singletons** — settings and page models (both carrying `revision` for optimistic locking), plus a Zod schema per page key under `validators/pages/` with a `Record<PageKey, …>` index, so adding a page key to the contract without adding its schema fails typecheck. Page sections are declared individually with real sub-schemas under `strict: 'throw'`, so a typo like `hreo` is rejected rather than stored and silently ignored; the per-key Zod schema then decides which sections that key must have. Validation errors carry a precise path (`whyChooseUs.points.0.icon`), which is what an editor gets back in `error.details[].path`. Notable: registering the eight page media fields exposed a real hole in the 2.2 registry guard — `eachPath` does not descend into sub-documents, so it reported nothing for `hero.image` and friends and **passed while they were unregistered**. Page documents hold eight of the registry's twelve entries, so that gap covered most of it. The guard now recurses into embedded sub-schemas, and I verified it fails on both a top-level and a nested omission. 21 new tests.
- **2.4 Seed script** — `npm run seed` loads `fixtures/seed/*`, minting Media records from the placeholder descriptors, resolving slug references to ObjectIds, and upserting everything by its natural key. Upserting rather than creating is the whole point: creating would hand each re-run to the slug collision logic and silently produce `tax-2`, `tax-3`, changing the site's URLs every time anyone reseeded — there is an explicit test that no suffixed slug appears after two runs. `runSeed()` is exported so tests drive it directly, and the production refusal takes its environment as an argument rather than reading frozen config, so the guard itself is tested (including that it writes nothing when it refuses). 15 new tests. **Phase 2 complete: `npm run check` green, 337 tests.**

## Phase 3: Public read API

- **3.1 Serializers** — image, person, insight, practice-area and office serializers, each returning a type alias from `types/api.ts` so a payload that drifts from the contract fails typecheck. Every output is additionally validated against the spec's own schema with ajv, which catches what the compiler cannot: an out-of-enum value, a pattern violation, or a stray property arriving through a spread. Notable: `sizes` moved onto the Media record (ADR-030) because the rule for forming them is provider-specific and unguessable from a URL. Rules encoded here rather than left to the frontend: `displayName` keeps only "Dr." and appends post-nominals; a null insight author means _the firm_, not a missing value; chips are first-category-then-practice-area with a documented fallback; and a video insight carries the Watch Video CTA. Two tests cover the forgotten-`.populate()` case, where an unpopulated ObjectId must read as absent rather than produce a half-built object. Attorney email is asserted absent from both person payloads. 28 new tests.
- **3.2 `/site`** — the global shell, with `optionalPreviewAuth` implemented now (token _verification_ is independent of Phase 4's token issuing, so preview genuinely works and is genuinely tested — including against a malformed token, one signed with the wrong secret, and an expired one). Draft exclusion for FAQs and practice areas is proved here, once, per ADR-029. Two things the tooling caught rather than review: the layer rule rejected `services` importing a serializer type, which moved to `interfaces/site.interface.ts`; and `expectToMatchContract` rejected a 404 the spec did not declare, so the spec gained a documented 404 for an unconfigured site _before_ the code was accepted. Serializer input types were narrowed to the fields they actually read, so `/site` can project four fields per practice area rather than loading whole documents on the critical path of every page load. In-process caching is deferred to 3.8, where `core/cache.ts` lands. 14 new tests.
- **3.3 / 3.4 / 3.5 Collections, people and insights** — all ten remaining public read endpoints, built together. Rules worth knowing: `role=partner` includes the managing partner (ADR-024), proved by a test; seniority sorting derives the role rank in an aggregation rather than storing it, so changing the ladder needs no migration; a job stops being public when closed _or_ past its closing date, and both are in the query so counts and pagination stay right; an unknown `practiceArea` filter returns an empty list rather than a 404, because the value comes from a filter tab. Two layer violations were caught and fixed while writing this: a controller making two service calls and assembling a payload inline (both moved into the service and a `toDetail` serializer), and a service importing a serializer type. Serializer inputs became structural minimums rather than `Omit<IDoc, …>` — which had the useful side effect of making attorney `email` _unrepresentable_ in a person payload rather than merely absent. 43 new tests.
- **3.6 / 3.7 / 3.8 Pages, search and caching** — all eight composed pages deep-equal their fixtures (ids and placeholder dimensions normalised). Getting there surfaced two real bugs the weaker assertion would have missed: insights sharing a `publishedAt` had **no deterministic tiebreaker**, so identical requests could return different orders — the query now sorts by `publishedAt, order, _id`; and four insights shared one cover-image placeholder key, so the seed deduped them into a single Media record with the wrong alt text. Search is published-only with no preview mode, deliberately, and that is asserted. Caching is tag-based: a practice-area write clears the shell plus the Home and Practice Areas pages but leaves Careers alone, which the test checks by count. Preview bypasses the cache and sends `no-store`, so a draft cannot reach a shared cache. A layer conflict in the docs was resolved: ARCHITECTURE said composers apply serializers while the layer table forbids services importing serializers, so services now fetch (`getPageSources`) and serializers shape (`toPage`), with the populated document shapes moved to `interfaces/populated.interface.ts` where both layers may see them. **Phase 3 complete: 469 tests, `npm run check` green.**

## Phase 4: Admin auth and RBAC

- **4.1 Admin auth spec** — 11 admin operations specified before any code: login, refresh, logout, me, the two 2FA steps, password change, user list/create/update, and the audit log. Notable contract decisions documented in the spec itself: the refresh token is _not_ in the login body (it is an httpOnly, SameSite=Strict cookie scoped to the auth path, so dashboard script cannot read it); a login that needs a code returns 401 with `TOTP_REQUIRED` in `details`, so the UI can tell "prompt for a code" from "wrong password"; replaying a revoked refresh token revokes the whole chain; and `AuditLogEntry.meta` is documented as never carrying personal data. ## Phase 5: Admin content API

- **5.1 Admin content spec** — 19 more operations: content CRUD (list, create, get, update, delete, publish, unpublish, reorder), settings and pages GET/PUT/PATCH, and the media library including in-place file replacement. Per-collection editable shapes are fully specified (`PracticeAreaAdmin`, `PersonAdmin`, …) with references as ids plus `_expanded` previews, so an admin GET body is a valid PUT body. Two decisions in ADR-033: the seven collections share one set of paths keyed by a `collection` enum rather than 56 near-identical operations; and those paths gained a `/content/` segment, because `/admin/{collection}` is genuinely ambiguous with `/admin/settings`, `/admin/pages/{key}` and `/admin/media/{id}` — correctness would otherwise depend on Express registration order. Spec lints with zero errors _and_ zero warnings.
- **5.2 / 5.5 / 5.6 CRUD factory, sanitisation and invalidation** — one implementation of list/get/create/update/delete/publish/unpublish/reorder serving all seven collections, with everything that differs between them in `constants/content-collections.ts`. Optimistic locking checks the revision inside the same `findOneAndUpdate` that applies the change, so two concurrent saves cannot both win; a missing `If-Match` is refused outright rather than falling back to last-write-wins. Deletes are blocked by a reference check that names what still points at the record. Rich text is sanitised inside the Zod schema, so a service never sees unsanitised HTML and no write path can forget to call the sanitiser — tested by storing a `<script>` and reading it back from the database, not just from the response. The revalidation webhook is fire-and-forget with a timeout, because the firm saving a page must not fail when the frontend is down. **A real bug surfaced here:** `adminUserRoutes.use(requireRole('admin'))` had no path, so it applied to _every_ `/admin/*` request passing through that mount — admin-only was silently the rule for the whole admin API, and an HR user could not reach jobs. All three admin routers now attach guards per route, and the role matrix table gained the content routes, which is the test that should have caught it. 50 new tests; 156 admin tests total.
- **5.1a Per-collection admin paths, and two guardrails (ADR-033 revision, ADR-034)** — the spec now lists all seven collections as explicit paths (35 paths, 56 operations), generated with their write schemas and example fixtures from one table by `scripts/generate-admin-content-spec.ts`, so the dashboard gets concrete per-collection types instead of a union it has to narrow. The implementation is unchanged behind them. Two tests that cannot be forgotten: the **route inventory** derives every admin route from the Express router stack and fails if one lacks an explicit role guard or a matrix entry, and the **draft canary** plants one unique string in unpublished content of every kind and calls every public GET in the spec, anonymously and with an unauthenticated `preview=true`, asserting it never comes back. Both were checked against a deliberately broken build before being trusted — which found the inventory's first version too weak, since it accepted `requireAuth` as proof of a role guard. `prettier --check .` joined `npm run check`. 979 tests pass.
- **5.3 Pages and settings** — the eight page documents and site settings share one implementation in `services/singleton.service.ts`, because the part worth getting right is identical for all nine: merge a section, validate the _result_, and save only over the revision the editor actually read. PATCH is a shallow merge by design — each top-level key replaces that section whole, so removing a stat or clearing a nested field is expressible, which a deep merge would make impossible. Two things surfaced while building it: a page document declares _every_ page's sections and defaults the unused ones to null, so a raw read of Home also carried `story` and `stats`, which would have made the admin GET body invalid as a PUT body; the read is now narrowed to the sections the key's own schema declares, so the round-trip guarantee holds for all 8 keys. And Zod reports every unrecognised key in one issue pointing at the _parent_, so a typo like `hreo` produced a 400 that named nothing — `zodIssueDetails` now splits them, and the dashboard gets the field to highlight. 32 new tests.
- **5.4 Media library** — upload, search, replace-in-place and delete, with both drivers real: the local one renders the three widths with sharp and writes them to disk, the Cloudinary one signs a multipart POST and serves the widths as `f_auto,q_auto` transformation URLs. Neither needs a credential to test — the local driver runs the production path in the suite, and the Cloudinary driver is asserted against a fake `fetch`, including the SHA-1 signature, because a wrong one fails only against the live service. The type check reads magic bytes and ignores both the filename and the declared `Content-Type`, since both are attacker-supplied; an SVG and an executable renamed `.png` are each rejected with 415. `findUsages` computes "where is this image used?" from `constants/media-refs.ts` on demand with one query per referencing model, which is what makes a delete safe to refuse and a replacement able to clear the caches of every page showing the picture. Replace keeps the id and changes the URL, in that order — store, repoint, then delete the old file, so a failure leaves an orphaned file rather than a live page pointing at nothing. 38 new tests; 1130 in total.
- **Phase 5 review fixes (ADR-035)** — the api-reviewer found four majors and eleven minors; all are fixed. The two that mattered most were silent: a duplicate slug reached the generic 500 handler, so an editor renaming a page to a taken URL saw "Something went wrong"; and media cache tags were built from the display label rather than the slug, emitting `practice-area:Tax` where the frontend revalidates `practice-area:tax` — a detail page that would have stayed stale for ever, invisible to the in-process cache the test was watching. Media joined optimistic locking (`revision` + `If-Match`), which also closed a race where two concurrent replacements each stored a file and both deleted the original, orphaning the loser's upload. A missing `If-Match` now answers 428, the status the spec had always declared. One test could not fail — the non-recursive `readdir` behind "removes the old file" never saw the driver's `YYYY/MM/` layout — and both guardrails were re-verified against a deliberately broken build afterwards. 1131 tests pass.

## Phase 6: Forms and submissions

- **6.1 Admin submission spec** — 10 operations over the three submission types: list, detail and a handling PATCH for enquiries, messages and applications, plus the signed CV link. Hand-written rather than generated, unlike the content collections: the three shapes genuinely differ, and a template would have been longer than the result. Two decisions are visible in the schemas. Only handling fields are patchable — status and assignment — so a record stays a faithful account of what was sent, and nothing a submitter typed can be edited after the fact. And the shapes withhold more than they show: `ipHash` and the user agent are stored for abuse investigation but never returned, `ApplicationCv` describes the file without its storage key, and the CV itself is reachable only through a five-minute signed URL whose every issue is audited. Spec lints with zero errors and zero warnings; 444 contract assertions pass.
- **6.2 Enquiries and messages** — both public JSON forms, with the order that matters: honeypot, captcha, store, then mail, so everything that can reject does so before anything is written. A bot gets 201 and a well-formed reference, because one told it was caught simply retries without the hidden field. Consent is stored as evidence — the wording version and the moment, not a boolean — since proving consent means proving what was consented to. The firm's notification carries the reference and a dashboard link and nothing else, which is asserted by searching the whole rendered email for the submitter's name, address, phone and words. Mail is best effort: losing an enquiry because a provider is down would be far worse than losing the notification about it. Two decisions came out of building it. The mailer ships as `resend` and `log` only (ADR-036): the SMTP driver would have meant a mail-transport dependency for something the brief does not ask for. And `core/logger.ts` now writes through a late-bound sink — pino resolves its destination once at construction, so the PII test could not otherwise see what redaction actually emitted; it caught a deliberately planted field name that no redaction rule covers, which is the point. 17 new tests.
- **6.3 Job applications** — the one public endpoint that accepts a file, so the order is the security property: honeypot, captcha, vacancy, magic bytes, virus scan, _then_ store. An infected file never reaches the firm's storage, which the test proves by spying on the storage driver rather than by trusting the sequence. A DOCX is recognised by finding `word/document.xml` in the archive's raw bytes rather than by unzipping it — decompressing untrusted input to identify it is what a zip bomb relies on. Both private drivers are real: the local one signs links with an HMAC over the key and expiry so it has the same shape of access control as S3, and the S3 driver implements SigV4 by hand (uploads signed with the payload hash, downloads as presigned query URLs that expire on their own, listing paginated so the orphan sweep cannot silently see one page). The AWS SDK would have been tens of megabytes for three operations; the signature is verified in the tests by recomputing it independently from the documented steps, because the only feedback AWS gives for a wrong one is a 403. CVs are stored under a random key, never the uploaded name. 32 new tests.
- **6.4 Reading submissions** — list, detail and a handling PATCH for each type, split by who the firm says should see them: business development takes enquiries and messages, HR takes applications and CVs, and an editor sees none of it. Every read of a _single_ record writes an audit entry before the data is returned, because the NDPA question the firm may one day have to answer — who looked at this? — is unanswerable unless it was recorded at the time; a list writes none, since a list discloses nothing worth attributing. The patch schemas contain only status and assignment, so there is no endpoint through which the firm could edit what a submitter wrote. The CV link is five minutes long, refused unless the scan came back clean, and audited on every issue. With S3 the presigned URL points at S3; with the local driver it points at one HMAC-signed route on this API, which is mounted only for that driver — so a production deployment serves no files from the API at all. 31 new tests.
- **6.5 Retention sweep** — a daily job deleting CV files whose application has been TTL-expired. It is driven from storage rather than from the database, because the records that would say what to delete are exactly the ones that no longer exist. The subtlety worth its own test: a CV is written to storage _before_ its record is created, so for a moment every upload in flight looks exactly like an orphan — the sweep therefore spares anything written in the last hour, and `IPrivateStorage.list()` returns a modification time so it can tell the difference. Writing that made the first draft's stub (`isOlderThan` returning true) obviously wrong; it would have documented a grace period it did not have. The timer is `unref`'d, so housekeeping never delays a container shutdown. 6 new tests; 1328 in total, all passing.
- **Phase 6 review fixes (ADR-037)** — two blockers, both invisible to a passing suite. The default mail driver logged every submitter's email address, and no test saw it because every integration test swaps the mailer out — including the two written to prove nothing leaks. And every S3 CV upload would have been rejected: `x-amz-acl` was sent but not signed, which SigV4 answers with a 403, so on the only production-safe storage driver no job application could have been submitted at all; the unit test had hardcoded the signed-header list and so pinned the bug rather than catching it. Beyond those: production now refuses every dev-only driver (the local private driver mounts an unauthenticated file route, `noop` calls every CV clean, `log` sends nothing); list reads are audited, since their rows carry the same personal data a detail view does; issuing a CV link uses an audit write that may _not_ fail quietly, and the handover is recorded separately from the issue; the submission serializers type-check against the contract again instead of casting it away; and the coverage test walks app → spec as well as spec → app, which is how an unspecified route reached the app in the first place. 1336 tests pass.
